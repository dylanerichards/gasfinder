# Gas Finder · San Francisco

Find the nearest gas station in San Francisco and get walking or driving
turn-by-turn directions to it.

**Live:** https://serene-bayou-74363-4b94bb71b5f2.herokuapp.com/

## Why

Your car breaks down and you need gas. That's the whole problem this app solves.
Gas Finder is laser-focused: it finds where you are and guides you to the nearest
station, with no fluff. And because a dead tank often means walking, it gives you
both walking and driving directions, so you can get there on foot or by car.

## What it does

- **Set your location** — browser geolocation, a curated SF landmark, or a live
  address search.
- **See the 5 nearest gas stations** — listed with distances and plotted on a map.
- **Pick a destination** — manually, or auto-pick the station with the **shortest
  walk** or **shortest drive**.
- **Get directions** — turn-by-turn walking or driving, with the route drawn on
  the map.

## Stack

Rails 8 · Vite · React 19 · Tailwind v4 · Leaflet · SQLite (ephemeral). Deployed
on Heroku; CI on GitHub Actions; tested with RSpec (request + Capybara/Cuprite
system specs). No API keys and no paid services — geocoding (Nominatim), gas-station
data (a committed OpenStreetMap snapshot), and routing (OSRM) are all keyless and
proxied through Rails.


## Known tradeoffs

- **Directions are a static preview, not live GPS navigation** — there's no
  turn-by-turn "navigation mode" that follows you and re-routes (a much larger
  feature: continuous geolocation, step tracking, re-routing).
- **Gas-station data comes from [Overture Maps](https://docs.overturemaps.org)**
  (current, keyless), generated by `script/fetch_sf_gas_stations.py` into
  `db/sf_gas_stations.json` and queried in-process, so lookups are instant and
  reliable. A background job refreshes it daily, and it's re-runnable by hand.
- **No error monitoring** — a hosted tracker like Sentry would mean sharing an
  account with reviewers, so it's intentionally left out; errors surface in the
  Rails logs and the browser console instead.

The layout is responsive and verified on mobile.


## Running locally

Requires Ruby (see `.ruby-version`) and Node (see `.node-version`).

```bash
bundle install
npm install
bin/dev            # runs Puma + Vite together (Procfile.dev)
```

Then open the app (Puma prints the port). `bin/dev` runs the Rails server and the
Vite dev server side by side.

## Tests & checks

```bash
bundle exec rspec       # request + system specs (system specs need Chrome)
npm test                # React component tests (Vitest + Testing Library)
bundle exec rubocop     # lint (rubocop-rails-omakase)
bin/brakeman            # security scan
```

A pre-push hook (`.githooks/pre-push`) runs them all before every push. Enable it
with `git config core.hooksPath .githooks`.

## Refreshing the gas-station data

`db/sf_gas_stations.json` is generated from [Overture Maps](https://docs.overturemaps.org)
by `script/fetch_sf_gas_stations.py` (every place in the SF bounding box tagged
`gas_station`).

In production a background job refreshes it **daily**. Set a cron expression and
the app reruns the generator in-process and reloads the dataset, with no restart,
separate worker, or database:

```bash
heroku config:set GAS_STATION_REFRESH_CRON="0 9 * * *"   # 09:00 UTC daily
```

Run it on demand, locally or on a dyno, with:

```bash
bin/rails gas_stations:refresh
```

The generator needs the Overture Python tooling. Since overturemaps can't be
`--user`-installed under Homebrew Python, use a venv; the job and the rake task
pick up `.venv` automatically (or set `OVERTURE_PYTHON`):

```bash
python3 -m venv .venv && .venv/bin/pip install overturemaps
```
